01能读懂的回答不一定能被程序使用

服务台系统需要的是标题、优先级和影响人数，而不是任意格式的一段文字。如果每次用字符串切分寻找“优先级：”，模型只要换一种措辞就可能让程序解析失败。结构化输出先定义字段契约，再让模型按契约返回结果，最后执行类型和约束校验。

这里有四个不同层次：文本可以读；文本是合法 JSON；JSON 满足 schema；字段表达的事实真实可靠。通过前一个层次不代表通过后一个。例如人数为 12 的对象可以满足 schema，但如果原始工单说的是 21 人，结构依然正确，事实却错了。

本页先用 PydanticOutputParser 看清“格式说明 → 模型文本 → 解析校验”的过程，再提供在线 with_structured_output 分支。结构化输出适合分类、抽取与应用接口，不应为了形式统一强迫所有自由文本对话都生成庞大 JSON。

02设计一个小而清楚的 schema

TicketSummary 有三个字段：非空且长度有限的标题、只能取 low/medium/high 的优先级，以及大于零的影响人数。extra='forbid' 拒绝未声明字段；人数使用严格整数，避免把字符串或小数悄悄转换后当成已验证数据。

这些约束应来自业务需要，不是为了把类型定义写得复杂。允许“未知”的字段就应该显式设计未知状态，例如可选人数或单独的证据字段，而不是鼓励模型为了满足必填而猜数。本例原文已经提供人数，便于集中学习验证；真实工单经常缺字段，必须单独处理。

字段说明帮助模型理解含义，但最终的数值范围、枚举和额外字段限制由程序执行。模型抽出的工单号、员工身份、权限范围，仍需到可信系统核实；不能因为它被装进 Pydantic 对象，就成为授权凭据。

03运行：成功对象与拒绝路径

执行 python examples/05_structured.py。依赖固定为 LangChain 1.2.0 与锁文件中的 Pydantic 等配套版本。默认离线运行，固定模型仅负责返回预设 JSON。

examples/05_structured.py下载源文件 ↗
"""结构化输出。依赖：langchain==1.2.0；完整版本见 requirements.lock.txt。

离线：python examples/05_structured.py
在线：python examples/05_structured.py --live
"""
import sys
from typing import Literal

from langchain_core.exceptions import OutputParserException
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import PydanticOutputParser
from langchain_core.prompts import ChatPromptTemplate
from pydantic import BaseModel, ConfigDict, Field


class TicketSummary(BaseModel):
    model_config = ConfigDict(extra="forbid")
    title: str = Field(min_length=1, max_length=80, description="简短工单标题")
    priority: Literal["low", "medium", "high"]
    affected_users: int = Field(ge=1, le=100000, strict=True)


def main() -> None:
    parser = PydanticOutputParser(pydantic_object=TicketSummary)
    prompt = ChatPromptTemplate.from_messages([
        ("system", "提取工单，不编造字段。{format_instructions}"),
        ("human", "{description}"),
    ]).partial(format_instructions=parser.get_format_instructions())
    description = "财务部 12 人无法登录系统，请按 high 优先级记录。"

    if "--live" in sys.argv:
        from common import live_model

        # 集成层处理结构化输出。需要所选提供商/模型支持该功能。
        extractor = live_model().with_structured_output(TicketSummary)
        result = extractor.invoke(description)
    else:
        fake = FakeListChatModel(responses=[
            '{"title":"财务系统登录失败","priority":"high","affected_users":12}'
        ])
        result = (prompt | fake | parser).invoke({"description": description})
        assert result.affected_users == 12
    assert isinstance(result, TicketSummary)
    print(result.model_dump_json())

    invalid = '{"title":"登录失败","priority":"urgent","affected_users":0}'
    try:
        parser.parse(invalid)
    except OutputParserException:
        print("非法枚举与人数：已正确拒绝")
    else:
        raise AssertionError("不满足业务 schema 的 JSON 不应通过")


if __name__ == "__main__":
    main()

应得到包含 priority='high' 和 affected_users=12 的对象，并看到“非法枚举与人数：已正确拒绝”。失败输入本身是合法 JSON，拒绝原因是它不符合业务 schema。这正是只做 json.loads 无法完成的检查。

get_format_instructions() 生成说明并放进提示；解析器在输出之后执行验证。这条链没有让模型预先保证所有结果合规。因此错误必须是预期的程序分支：记录失败类别，必要时在预算内重试，或转交人工补充信息。

04三种接入位置，不要混在一起

方式使用位置结果与限制
PydanticOutputParser普通链的输出端解析模型文本；格式失败会抛异常
model.with_structured_output单次模型调用由模型集成提供支持；能力取决于提供商和模型
create_agent(response_format=...)Agent 最终输出使用 Agent 的结构化输出机制；从 structured_response 读取对象

在 Agent 中，可以明确选用 ToolStrategy 或 ProviderStrategy。前者利用工具调用协议表达结果，后者利用提供商原生结构化输出；都必须考虑所选模型的能力。使用 schema 类型的自动策略选择时，更应检查当前锁定版本与模型配置，不要把最新文档示例直接套进历史版本。

在线演示执行 python examples/05_structured.py --live，复用环境页设置的模型与密钥。它使用模型级结构化输出。真实输出的标题可能不同，因此验收关注类型、约束与原文事实，而不是逐字匹配。离线分支不能证明提供商支持该能力。

05练习：验证比格式更进一步

  1. 入门：把有效 JSON 的人数改成 0，直接调用 parser.parse。验收条件：捕获 OutputParserException，程序不得继续创建工单。
  2. 进阶：增加一个只允许“软件”或“硬件”的类别字段，并同步修改固定模型数据。分别测试缺字段和非法类别，确认都被拒绝。
  3. 挑战：准备三条测试输入：合法对象、合法 JSON 但非法字段、结构合法但事实与原文不符。分别记录结构校验与事实校验结果。验收条件：第三条不能被错误记为“事实正确”，说明需要另外设计证据核对。
参考判断

结构校验可以完全自动化。对本例的事实校验，可以直接比较原文已明确提供的人数；更复杂的事实需要可信来源或人工标注。模型给出的自评置信度不能替代该检查。

06常见误区与最佳实践

  • 不要删除错误输出后假装成功。保留脱敏后的失败类别与 schema 版本，便于定位是提示、模型能力还是数据问题。
  • 不要无限“修复 JSON”。修复可能改变含义，还会增加延迟和费用。先明确最大尝试次数，失败后提供可恢复路径。
  • 不要把结构化结果当作安全命令。金额、账号、工具参数即使校验通过，仍需授权、业务规则与幂等检查。
  • 缩小输出面。只返回下游实际需要的字段。字段越多，缺失、矛盾、泄露和升级不兼容的可能性越大。

07从数据到行动

输出 schema 规定“模型交给程序什么数据”；06 工具调用会进一步规定“模型可以请求程序做什么”。两者共享类型约束思想，但工具可能产生副作用，需要更严格的执行边界。
