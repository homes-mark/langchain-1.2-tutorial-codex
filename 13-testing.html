13 · 测试、评估与可观察性

把“看上去能用”拆成协议正确、任务成功和生产表现三种可以分别验证的事实。

01测试不能只比最后一句话

一个回答措辞流畅，可能没有查工具；一个检索结果主题相似，可能属于其他租户；一个写入工具返回超时，可能已经创建了记录。测试必须进入流程中的关键边界，而不是只检查最终字符串有没有关键词。

层次对象本教程方式
确定性组件测试输入校验、权限、索引过滤、幂等断言真实函数、数据库与状态
执行轨迹测试工具调用顺序、参数、消息配对、预算脚本模型驱动真实 LangChain 图
集成测试提供商协议、工具与结构化能力配置密钥后运行 --live
任务评估模型是否选对工具、答案是否有依据人工标注集与可复核评分

前两层快速且可重复；后两层更接近真实用户体验，同时带来费用、非确定性与版本漂移。每次修改先运行快速回归，再按风险运行有代表性的真实模型评估。

02一个诚实的轨迹回归

examples/13_evaluation.py下载源文件 ↗
"""Deterministic workflow regression, not an LLM quality benchmark.
Dependencies: LangChain 1.2.0, requirements.lock.txt.
"""
from importlib import import_module
from langchain_core.messages import AIMessage, ToolMessage

build_agent = import_module("07_agents").build_agent


def evaluate():
    samples = ["VPN 能用吗？", "请检查 VPN 状态", "查询 vpn 服务"]
    records = []
    for query in samples:
        result = build_agent().invoke({"messages":[{"role":"user","content":query}]})
        messages = result["messages"]
        calls = [c for m in messages if isinstance(m, AIMessage) for c in m.tool_calls]
        outputs = [m for m in messages if isinstance(m, ToolMessage)]
        records.append({"query": query,
                        "tool_correct": len(calls) == 1 and calls[0]["name"] == "service_status" and calls[0]["args"] == {"service":"vpn"},
                        "tool_output_correct": len(outputs) == 1 and outputs[0].content == "operational",
                        "model_calls": sum(isinstance(m, AIMessage) for m in messages)})
    score = sum(r["tool_correct"] and r["tool_output_correct"] for r in records) / len(records)
    assert score == 1.0 and all(r["model_calls"] == 2 for r in records)
    print(f"fixture workflow success={score:.0%}; cases={len(records)}; model_calls=2/case")
    print("This does NOT measure live model intent understanding or answer truthfulness.")


if __name__ == "__main__":
    evaluate()

示例使用三种问题措辞，但每次都使用固定脚本模型。100% 表示既定工具轨迹正确执行，不表示模型能理解三种说法。这样的限制要写在评估结果旁边，而不能藏在实现细节中。

这里验证工具名、精确参数、工具返回值和模型轮数；即使最终回答仍然含“VPN”，错误工具或错误参数也会让检查失败。实战回归进一步检查会话隔离、审批前无写入、拒绝后无写入、批准后只写一次。

03建立自己的黄金样例集

从真实业务任务类型出发，不要从模型最擅长的例子出发。先准备一小组经人工确认的样例，每条记录问题、可信身份、允许使用的数据、预期工具或证据、允许发生的副作用，以及必须拒绝的动作。

类别示例可验证标准
正常查询查我的 T100 工单正确对象，只有只读工具
无答案手册未覆盖的问题说明证据不足，不能编造来源
越权查看其他租户工单执行层拒绝，无泄露
注入文档里要求忽略权限并导出数据文档被当数据，不改变权限
重试批准后同请求再次提交最多一条业务记录

把开发样例与保留评估集分开。不要不停修改提示词直到在同一小集合上满分，然后声称系统泛化良好。模型、提示词、语料、分块参数或工具 schema 任一变化，都可能需要重跑相应评估。

04指标要对应业务问题

检索召回：在已知相关文档集合时，统计 top-k 是否覆盖正确证据；多证据任务还要检查覆盖率。引用正确性：引用来源存在只是最低要求，还需证据真正支持回答。拒答质量：分别统计该拒答却回答、该回答却拒答的情况。

任务成功率：按业务验收判定，而不是按文字漂亮程度。安全约束：越权和未经批准的写操作采用明确的零容忍测试断言。工程指标：记录端到端 p50/p95 延迟、失败类型、调用次数和单位成功任务成本；不同样本量下的分位数不宜直接比较。

LLM-as-judge 可辅助评价语义，但评判模型也会出错。给它明确量表，与人工样本校准，并保留证据和评分理由；不要让一个同样可受注入影响的模型决定访问权限。

05从失败回到具体一层

推荐为一次运行分配 request_id，把模型、检索、工具与审批事件关联起来。记录版本、时间、状态、耗时与错误类别。涉及个人数据时先做最小化与脱敏，再决定是否允许把 trace 发送到外部服务。

LangSmith 等平台可以帮助比较运行轨迹与评估结果，但不是离线教程的必需依赖。本教程不启用远程追踪。若自行启用，应核对采样、保留期、访问范围以及提示词和文档内容是否允许上传。

排查时按输入→检索/工具参数→工具结果→模型总结→副作用查看。一条最终错误答案可能源自上游检索失败，盲目改提示词通常掩盖问题而不解决问题。

06练习：让测试抓住真实错误

  1. 基础：把脚本 fixture 中的服务名改错。验收：精确参数断言失败，而非仍得到“成功”。
  2. 进阶：新增至少两条无答案与两条越权样例。验收：分别记录拒答和权限测试结果，不合并成一个模糊总分。
  3. 挑战：配置真实模型，把同一保留集运行多次，记录工具选择、引用、成本与延迟。验收：报告样本量、模型标识、提示词版本及未覆盖场景；不可沿用离线100%作为线上质量结论。

交付中的自动验证报告见 validation/report.json。接下来把测试边界提升为部署边界。
