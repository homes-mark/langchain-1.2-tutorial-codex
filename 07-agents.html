01Agent 的新能力与新责任

固定链由开发者预先确定步骤：模板 → 模型 → 解析器。Agent 在每次模型回复后检查工具请求：如果有，就执行工具并把结果加入消息，再调用模型；如果没有，通常返回最终答案。循环扩大了处理复杂任务的能力，也引入了循环次数、工具权限和结果可信度的新问题。

在 1.2 主路径中，使用 from langchain.agents import create_agent。它构建在 LangGraph 之上，提供消息状态、工具执行和中间件集成。你无需先掌握底层图 API；当任务需要固定分支、复杂并行或显式状态机时，再考虑直接编排 LangGraph。

“Agent 会思考”不是一个足够精确的工程描述。你能观察和验证的是它发出的消息、工具名、参数、工具结果、最终回答与外部副作用。不要依赖不可观测的内部推理作为审计证据。

需求合适起点理由
把文本提取成固定字段模板 + 结构化模型/解析器不需要动态选步骤
先检索再回答固定 RAG 链每次流程相同
按故障情况选择查询工具Agent下一步取决于前一步观察

02完整的单工具 Agent

examples/07_agents.py下载源文件 ↗
"""LangChain 1.2.0; full versions: requirements.lock.txt. Optional: --live."""
import argparse
from langchain.agents import create_agent
from langchain.tools import tool
from langchain_core.messages import AIMessage, ToolMessage
from common import ScriptedChatModel, live_model


@tool
def service_status(service: str) -> str:
    """Read a demo service status. Supported service: vpn. No external IO."""
    return {"vpn": "operational"}.get(service.lower(), "unknown service")


def build_agent(live=False):
    model = live_model() if live else ScriptedChatModel(responses=[
        AIMessage(content="", tool_calls=[{"name": "service_status", "args": {"service": "vpn"}, "id": "status-1", "type": "tool_call"}]),
        AIMessage(content="VPN 服务运行正常（operational）。"),
    ])
    return create_agent(model, tools=[service_status], system_prompt="用中文回答。服务状态必须查询工具；未知服务说明无法确认。")


if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--live", action="store_true")
    args = parser.parse_args()
    result = build_agent(args.live).invoke(
        {"messages": [{"role": "user", "content": "请查询 VPN 服务是否正常。"}]},
        config={"recursion_limit": 12},
    )
    for message in result["messages"]:
        print(message.type, message.content, getattr(message, "tool_calls", ""))
    if not args.live:
        assert [m.type for m in result["messages"]] == ["human", "ai", "tool", "ai"]
        assert next(m for m in result["messages"] if isinstance(m, ToolMessage)).content == "operational"
        # New model instance: scripted responses are consumed, not reusable data.
        steps = list(build_agent().stream({"messages": [{"role":"user", "content":"VPN?"}]}, stream_mode="updates"))
        assert [list(x)[0] for x in steps] == ["model", "tools", "model"]
        print("PASS: tool loop and stream updates = model -> tools -> model")

离线模型预先安排了一次 service_status 工具请求，随后返回中文结果。真实工具函数会执行，真实图会把工具结果放回状态；固定脚本不会读取自然语言后自行推断参数。在线分支使用同一工具与提示词，由模型自行选择工具。

预期验证：消息类型依次为 human, ai, tool, ai，工具结果为 operational，最后出现 PASS。第一次 ai 的正文可以为空，因为有效内容在 tool_calls 中。不要把空正文当作模型失败。

03读懂结果和边界

agent.invoke() 返回状态字典，常见入口是 result["messages"]，不是裸字符串。为了显示给用户，可以读取最后一条消息；为了测试与审计，则要检查中间工具请求及其结果。配置结构化输出时还会有 structured_response，见 05。

工具应接收可验证的参数，返回短小、稳定的业务数据。服务列表、权限判断和错误分类在代码层处理；系统提示词负责告诉模型如何使用这些能力。即使提示词说“只能查自己的工单”，执行层仍必须检查真实身份。

recursion_limit 限制图的执行步数，不等同于“最多调用这么多次模型”。它可以阻止无限循环，但精确的模型调用预算应使用 12 的 ModelCallLimitMiddleware。超限应向用户报告未完成任务，不能把一条截断回答当作成功。

04观察步骤，而不猜测内部状态

示例还使用 stream_mode="updates" 收集节点状态更新。这个简单图会出现 model → tools → model，对应发起请求、执行工具、形成回答。中间件可能增加其他节点，因此不要把这三个名字当成所有 Agent 的固定轨迹。

1.2 的常见流式模式包括 updates（步骤更新）、messages（消息分块及元数据）和 custom（自定义进度）。固定脚本模型没有真正的 token 生成过程，本例用步骤流来验证可观察性。真实 token 流还取决于提供商和模型支持。

当前文档展示的 stream_events(..., version="v3") 是后续版本的接口，不能直接复制到本教程环境。学习旧版本时，文档中的“推荐”不一定适用于锁定版本。

05最容易踩的三个坑

  • 重复绑定工具：本教程把原始模型和 tools 交给 create_agent。不要把手动 bind_tools 的模型当成所有配置都通用的输入，尤其结构化输出会参与绑定。
  • 工具返回大段无关数据：会增加上下文成本，还可能淹没有效证据。限定字段、数量和长度，把完整日志留在受控存储中。
  • 把工具的成功执行等同任务成功：工具可能查错对象，模型也可能曲解结果。验收必须同时覆盖参数、返回值与最终结论。

06从闭环到可控决策

  1. 基础：打印每条消息的类型与工具调用 ID。验收：ToolMessage 与 AI 工具请求的 ID 对应。
  2. 进阶：增加只读服务 mail，修改脚本 fixture 对应参数，再运行在线分支对比。验收：离线证明新路径执行正确；在线另测模型是否正确选择。
  3. 挑战：让脚本连续发起多个查询，设置较小预算。验收：任务被明确限制；不能把图步数解释成模型调用数，详细实现见 12。
