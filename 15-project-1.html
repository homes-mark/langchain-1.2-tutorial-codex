实战 1 · 单工具企业服务台

从一个可验证的只读问题开始：查询自己的工单。五阶段共享实现，每一步只增加一种主要能力。

01业务目标与五阶段路线

你在一家企业维护 IT 服务台。员工 Alice 想知道自己的 VPN 工单是否处理完成。第一版只回答工单状态；随后再加入服务健康状态、多轮追问、企业知识和审批建单。贯穿案例的价值在于，每次扩展都能指出新增了哪个状态、哪个信任边界、哪条验收断言。

阶段新增能力可观察的证据
1单只读工具ToolMessage 返回 IT-1001 的状态
2多工具工单和服务健康各有独立回执
3会话记忆同一 thread 保留上一轮消息
4权限过滤后的 RAG只引用当前用户可读的 KB-001
5审批、幂等、审计批准后恰好一条工单、一条审计

这是企业架构的可运行教学切片。数据表是虚构业务数据，身份由演示程序固定生成，数据库是临时 SQLite；它还不是接入了企业 SSO、真实工单系统和持久队列的上线服务。

02先划清数据和授权边界

模型只应提供 ticket_id，不能自行指定 tenant_id 或 user_id。后端将认证后的身份作为 RequestContext 传入；工具通过 ToolRuntime 读取。参数不出现在模型可填写的输入里，比在提示词中要求“不要冒充别人”更可靠。

project/helpdesk.py下载源文件 ↗
@dataclass(frozen=True)
class RequestContext:
    # 生产环境应由登录会话/后端生成；不接受模型或浏览器直接指定身份。
    tenant_id: str
    user_id: str
    roles: tuple[str, ...]
    request_id: str
    db_path: str

本案例在查询时同时检查租户和工单所有者。无权限与不存在统一返回 NOT_FOUND_OR_FORBIDDEN，避免通过不同错误提示枚举其他人的工单。管理员特例写在执行侧，升级角色应由真实身份系统处理。

project/helpdesk.py下载源文件 ↗
def lookup_ticket(ticket_id: str, context: RequestContext) -> dict:
    record = TICKETS.get(ticket_id)
    if not record or record["tenant"] != context.tenant_id:
        return {"error": "NOT_FOUND_OR_FORBIDDEN"}
    if record["owner"] != context.user_id and "admin" not in context.roles:
        return {"error": "NOT_FOUND_OR_FORBIDDEN"}
    return {"ticket_id": ticket_id, "status": record["status"]}

这里的 dataclass 只是承载上下文，并不完成认证。将任意请求 JSON 反序列化为这个类再交给 Agent，仍然会产生身份伪造漏洞。

默认的 ScriptedChatModel 按预设顺序发出工具调用和最终文本。这使你能够离线检查参数、执行、回传及结束条件；它没有阅读问题并自行规划的能力。可运行的框架控制流，与真实大模型的理解质量，是两项不同的验收工作。

04如何判断阶段一完成

默认运行应出现工具回执 {"ticket_id":"IT-1001","status":"处理中"}，最终文本包含工单号与状态，数据库行数为 tickets=0, audit=0。单独检查最后一句自然语言是不够的：脚本模型甚至可以说出不存在的事实。应检查执行记录确实出现了 get_ticket，并读取其结构化结果。

读工具无副作用，适合作为第一条基线。后续重构、升级模型或者添加中间件时，至少保留这条基线，避免功能增加后原本的查询反而失效。不能把来自模型的“已经查询”当作查询发生的证明。

05练习：成功路径、失败路径、授权路径

  1. 入门：运行阶段一，在输出中标注用户请求、工具回执和最终回复。验证：能解释 status 字段来自 TICKETS，而不是提示模板。
  2. 进阶：把脚本模型中的 IT-1001 改为一个不存在的编号。验证：工具返回 NOT_FOUND_OR_FORBIDDEN；说明为什么还应同步调整脚本最终文本，或只针对工具结果做断言。
  3. 高级：用同租户其他用户以及不同租户身份调用 lookup_ticket。验证：两类越权均返回相同错误，不能泄露状态。参考 check_project.py 的边界检查。

06误区与进入下一阶段的条件

误区：把“提示词已经写了权限规则”当作授权；把模型回答正确一次当作工具可靠；把演示身份当作真正登录。授权必须在工具触达数据时检查，业务结果必须以数据源为准。

最佳实践：第一版只暴露最小只读能力，工具名描述业务动作，输入 schema 足够窄，错误码稳定。避免把一个可执行任意 SQL 或任意 URL 的万能工具交给模型。

完成三个练习后继续 实战 2：多工具协作。新增第二个数据源时，观察的重点从单个工具是否可用，转为两个结果如何组合并保持各自的来源。
