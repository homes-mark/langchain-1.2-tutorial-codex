02 · 模型与消息：认识一次调用

从消息角色、输入输出类型和一次模型调用开始，建立后续模板、链、工具与记忆共同使用的数据模型。

01先理解模型边界

把企业 IT 助手看成一个普通程序：程序接收用户问题，组织上下文，调用模型，再把结果交给页面或后续业务。LangChain 的职责是统一这些组件的接口。模型仍然来自某个提供商或本地推理服务；安装 LangChain 不会自动下载一个大模型，也不会让模型知道你的公司制度。

本教程锁定 Python 包 langchain==1.2.0，基础类型位于 langchain_core，提供商适配位于各自的集成包。这里使用 FakeListChatModel 离线验证接口，再通过同一调用位置切换在线模型。固定回答只是测试数据，不能据此判断模型是否理解了问题。

一次调用的最小边界是：消息列表 → 聊天模型 → AIMessage。先掌握这个边界，再学习提示模板如何生成消息、链如何连接组件、Agent 如何把工具结果补回消息列表。

02四种消息角色

类型表达什么本项目中的例子
SystemMessage应用设置的行为约束和任务背景你是 IT 助手，只根据授权资料回答
HumanMessage用户本轮提供的输入我无法登录财务系统
AIMessage模型回复，也可能包含工具调用请求请补充错误码，或请求查询工单
ToolMessage一次工具执行的结果工单 T-100 当前状态为处理中

消息不是简单的带标签字符串。除 content 外，消息还可能携带 ID、用量信息、工具调用及其他元数据。不要为了方便记录日志就把整个对象强行转成字符串，否则后续很难可靠地读取结构化字段。

AIMessage.content 在纯文本示例中是字符串，在多模态或某些提供商接口中也可能是内容块列表。这里的断言只针对本章固定的纯文本测试数据。业务代码需要按所用模型支持的内容结构处理图片、文本和其他块，不能无条件拼接成普通字符串。

03运行：一次调用与流式合并

在教程根目录、已安装锁文件依赖的环境中执行 python examples/02_messages.py。以下是完整文件，默认不联网，不需要密钥。

examples/02_messages.py下载源文件 ↗
"""消息与模型。依赖：langchain==1.2.0；完整版本见 requirements.lock.txt。

离线：python examples/02_messages.py
在线：python examples/02_messages.py --live（先配置模型环境变量）
"""
import sys

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage


def main() -> None:
    messages = [
        SystemMessage(content="你是企业 IT 助手。用中文简短回答。"),
        HumanMessage(content="密码重置前应先完成什么？"),
    ]
    if "--live" in sys.argv:
        from common import live_model

        model = live_model()
    else:
        # 真正运行 LangChain 接口，但回答是固定测试数据，不具有推理能力。
        model = FakeListChatModel(responses=["先完成身份验证。"])

    response = model.invoke(messages)
    assert isinstance(response, AIMessage)
    print("消息角色：", [message.type for message in messages])
    print("模型回复：", response.content)

    # 模型对象不会替你保留聊天历史；下一次调用应显式传入历史。
    history = [*messages, response, HumanMessage(content="为什么？")]
    assert len(history) == 4
    print("下一轮消息数：", len(history))

    # 仅演示离线流式接口，避免在线例子额外计费。
    streaming_model = FakeListChatModel(responses=["身份验证"])
    text = "".join(chunk.content for chunk in streaming_model.stream(messages))
    assert text == "身份验证"
    print("流式合并：", text)


if __name__ == "__main__":
    main()

你会看到消息角色 ['system', 'human']、固定回复“先完成身份验证。”、下一轮消息数 4，以及流式合并结果“身份验证”。这些检查验证的是消息类型、历史组织和流式片段拼接；不会验证在线模型的回答质量。

代码没有把第二轮历史真正发给模型，只构造并检查了四条消息。这样能清楚看出“保存历史”是应用的责任。流式输出中的片段是一段响应的分块，不代表模型已经完成了整个答案。

04接上真实模型

按环境页设置 OPENAI_API_KEY 和 OPENAI_MODEL 后，执行 python examples/02_messages.py --live。模型名由你有权限使用的服务决定；教程不把某个模型名称和服务可用性写死。在线运行会联网并可能计费，离线浏览 HTML 与离线运行固定示例不受影响。

在线分支仍然返回 AIMessage，但具体措辞可能变化，所以代码只断言类型，不把某一句话当作标准答案。第一次调试可以记录请求耗时、模型名与成功状态；不要直接打印密钥或未经脱敏的员工问题。提供商返回用量信息时再读取 usage_metadata，不要假设每次响应都包含它。

05练习：从查看数据到验证历史

  1. 入门：修改用户问题，并在调用前打印 messages[-1].content。验证打印的文本等于新问题，而离线模型回答仍保持不变。解释为什么这说明固定模型不能验证语义能力。
  2. 进阶：真正调用 model.invoke(history)，检查返回类型仍为 AIMessage。用一个变量分别保存第一轮和第二轮结果，确认你没有把消息对象覆盖成字符串。
  3. 挑战：把两个不同用户的消息分别放入两份列表，添加一轮历史后检查另一份列表长度不变。验收条件：会话 A 的内容没有出现在会话 B 的输入中。后续记忆章节会把这种隔离落实到线程 ID 和存储。
参考检查思路

新建列表时使用独立列表或 [*messages, response]；不要让两个用户变量指向同一个可变列表。离线模型只能验证“历史是否被传入”，真实模型是否利用历史还需要在线集成测试。

06常见误区与最佳实践

  • 误区：模型对象等于聊天会话。重复调用同一个模型实例通常不会自动附带历史。明确构造历史，或在后续 Agent 中使用 checkpointer。
  • 误区：system 提示能替代权限控制。提示帮助模型遵循行为要求，但读取数据库、操作工单的权限必须由服务端代码检查。
  • 实践：区分接口测试与质量评估。固定模型适合快速回归；真实模型需要小规模、可审查的样本集。不要把固定测试通过写成模型准确率。
  • 实践：先控制调用次数。流式提升用户感知，不会自动减少 token。调试时显式设置超时、重试上限，避免一次失败带来重复费用。

07学完这一页后

你应能说清一次调用的输入和输出，并指出聊天历史存在于哪里。推荐下一步学习 03 提示模板，把手工创建消息变成可复用、可检查的输入过程；完成后再进入 04 链与 LCEL。
