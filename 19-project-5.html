01写入前新增一道独立审批门

最终需求是：查询状态、检索处理办法后，为员工创建一张新工单。此前所有工具都是只读，现在 create_ticket 会修改数据库。模型可以提出动作与标题，但批准动作必须来自操作员；用户对话里出现“我已经批准”并不能代替审批通道。

共享构造器为 create_ticket 注册 HumanInTheLoopMiddleware，只允许 approve 和 reject。执行到待审批调用时，Agent 返回 __interrupt__，写工具尚未执行。随后应用使用相同 thread 的 config 和可信上下文，提交 Command(resume=...) 继续。

本教程固定 langchain==1.2.0。当前官方网页可能展示更晚版本的条件审批 when 或 per_call 模式，本代码没有使用这些接口。1.2 基本批量审批的 decisions 必须按 action_requests 的顺序给出，不能将审批列表随意重排。

                    decision = "pending"

                # decision 来自可信本地 CLI 操作员；绝不从模型回复中解析 approve。
                requests = result["__interrupt__"][0].value["action_requests"]
                decisions = [{"type": decision, **({"message": "操作员拒绝建单"}
                              if decision == "reject" else {})} for _ in requests]
                result = agent.invoke(Command(resume={"decisions": decisions}),
                                      config=config, context=context)

默认命令仅展示待执行动作并结束，数据库无写入。离线 --decision approve 是本地操作员对固定演示动作的显式决策；reject 会跳过动作并将拒绝原因返回 Agent。批准来源不是模型参数，create_ticket 的 schema 也没有 approved 字段。

在线模型提出的动作不可预知，所以 --live 模式即使带了 decision 参数，程序仍会先打印具体工具和参数，再要求在终端输入 approve 或 reject。输入其他内容继续保持暂停。这是本地教学审批界面；生产系统需要经过认证的审批端点，校验审批人、动作版本、会话归属和有效期。

本例使用 InMemorySaver，并在每次 CLI 运行创建新临时数据库。再次运行命令会重新演示一个流程，不会恢复上一次进程的中断。跨进程恢复需要持久 checkpointer 和可查找的待审批记录，不能只保留 thread_id。

03幂等键必须绑定可信请求

project/helpdesk.py下载源文件 ↗
def write_ticket(title: str, context: RequestContext) -> dict:
    """仅由已通过审批门的工具调用；真实业务服务还需独立验证审批凭据。"""
    if "requester" not in context.roles:
        raise PermissionError("当前身份没有建单权限")
    title = title.strip()
    if not 1 <= len(title) <= 120:
        raise ValueError("标题须为 1～120 个字符")
    payload_hash = hashlib.sha256(
        json.dumps([context.user_id, title], ensure_ascii=False).encode()
    ).hexdigest()
    with closing(sqlite3.connect(context.db_path)) as connection, connection:
        # 唯一约束负责重放去重；先查询再插入无法解决并发竞争。
        cursor = connection.execute(
            "INSERT INTO tickets (tenant,request_id,user_id,title,payload_hash) "
            "VALUES (?,?,?,?,?) ON CONFLICT(tenant,request_id) DO NOTHING",
            (context.tenant_id, context.request_id, context.user_id, title, payload_hash),
        )
        row = connection.execute(
            "SELECT id,payload_hash FROM tickets WHERE tenant=? AND request_id=?",
            (context.tenant_id, context.request_id),
        ).fetchone()
        if row[1] != payload_hash:
            raise ValueError("同一幂等键的操作内容发生变化")
        created = cursor.rowcount == 1
        if created:
            connection.execute(
                "INSERT INTO audit (tenant,user_id,request_id,action,ticket_id) "
                "VALUES (?,?,?,?,?)",
                (context.tenant_id, context.user_id, context.request_id, "create_ticket", row[0]),
            )
    return {"ticket_id": f"NEW-{row[0]}", "created": created}

request_id 在 RequestContext 中由应用提供，不让模型自由生成。数据库建立 (tenant, request_id) 唯一约束；同一请求重复执行时返回原工单。标题和用户身份组成 payload_hash：同一个键若对应不同内容则报错，避免把另一项请求误当作重试。

工单插入与创建成功审计位于同一事务。重复请求不会新增第二条成功审计，拒绝审批也不会产生成功记录。真实系统通常还需要独立记录“提出、批准、拒绝、失败”等全生命周期事件；本例的 audit 表只覆盖成功写入，不冒充完整审计平台。

幂等不是唯一一次执行的魔法。调用外部工单 API 时，要由对方支持幂等键，或者设计可靠的 outbox 与对账；本地事务无法回滚一个已发送的外部请求。SQLite 示例只证明单库事务边界。

05练习：正常执行与恶劣路径

  1. 入门：分别运行 pending、reject、approve，解释为什么前两者没有任何工单行。验证：成功审计与成功工单数量一致。
  2. 进阶：对同一 RequestContext 连续调用两次 write_ticket，再修改标题重试。验证：前两次返回同一 ID，修改标题时拒绝；演示命令见 check_project.py。
  3. 高级：将临时库改为测试环境的持久库，模拟应用在写入后、回复前崩溃。重放时必须复用可信 request_id，验证不重复建单。另写审批后撤权用例，确保工具执行时再次检查角色，而不是仅凭旧批准放行。

06完成项目与上线之前

五阶段通过意味着框架流程与关键本地边界可重复验证。上线还需要接入真实身份、持久化检查点、受认证审批界面、业务服务端权限与审批凭据校验、超时和预算、敏感信息治理、负载测试、灾难恢复和端到端真实模型评测。不要把一个演示通过的检查表当成这些设施已经存在。

安全边界应能在模型完全不配合时仍然成立。检索文档要求导出他人数据，工具应拒绝；模型重复建单，数据库应去重；用户冒充审批人，审批入口应拒绝；服务重试，审计应能解释最终发生了什么。

回看 生产实践，再到 版本迁移 制定升级回归。你现在拥有的是可演进的企业助手骨架，以及一组比“能聊两句”更具体的验收证据。
