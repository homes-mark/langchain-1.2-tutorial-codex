06 · 工具调用：请求、执行与结果回传

用安全的采购计算器拆解工具调用协议，理解模型提出请求、应用执行工具、模型整理结果的完整闭环。

01工具调用不是模型直接运行 Python

模型可以生成文字，也可以按工具协议提出结构化请求。例如采购问题中，模型请求调用 calculate_total，并提供数量与单价。真正执行乘法的是应用中的 Python 函数。这个分工让程序可以检查参数、限制允许的动作，并把执行结果作为事实来源交回模型。

完整闭环是：声明工具 → 把 schema 提供给模型 → 接收 AIMessage.tool_calls → 应用校验与执行 → 生成 ToolMessage → 模型整理答复。其中 bind_tools 只让模型知道工具定义，并不自动执行函数。到下一章，Agent 才会替你编排重复的模型与工具循环。

本页选择“只计算、不下单”的工具，是为了先学会协议。企业工具后来可能读取员工资料、创建工单或变更配置。功能变化之后，身份、权限、幂等与人工批准必须由应用负责，不能只在工具说明里写“请谨慎”。

02工具契约要让模型和程序都能理解

@tool 将有类型说明和文档字符串的函数包装成工具。函数名说明动作，说明文本告诉模型何时使用，参数 schema 约束实际输入。本例把单价写为整数“分”，避开二进制浮点表示金额的误差；名称也明确包含单位，减少模型把 19.90 元误当成 19.90 分。

Pydantic 将数量限制为 1 到 1000、单价限制为合理范围，并拒绝未知字段。限制是本教学场景的业务规则，不是 LangChain 固有规则。若接入真实采购系统，应使用实际规则，并在服务端再次验证商品价格；不能相信模型自己提供的单价。

工具只计算一个有限表达式，不接收任意 Python、Shell 或 SQL。不要为了实现“万能计算器”直接执行模型生成的代码。范围明确的工具更容易理解、测试、审计，也更容易提供准确的错误反馈。

03运行：手动完成一轮工具调用

执行 python examples/06_tools.py。依赖为 LangChain 1.2.0 与完整锁文件。离线 ScriptedChatModel 按预设返回工具请求和最终回复；真实的参数校验、工具执行、消息构造仍由 LangChain 与 Python 完成。

"""工具调用闭环。依赖：langchain==1.2.0；完整版本见 requirements.lock.txt。

离线：python examples/06_tools.py
在线：python examples/06_tools.py --live（模型须支持 tool calling）
"""
import json
import sys

from langchain.tools import tool
from langchain_core.messages import AIMessage, HumanMessage, ToolMessage
from pydantic import BaseModel, ConfigDict, Field, ValidationError

from common import ScriptedChatModel


class TotalInput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    quantity: int = Field(ge=1, le=1000, strict=True, description="采购数量")
    unit_price_cents: int = Field(
        ge=0, le=1000000, strict=True, description="单价，单位为分"
    )


@tool(args_schema=TotalInput)
def calculate_total(quantity: int, unit_price_cents: int) -> dict:
    """计算采购总价，使用整数分；仅计算，不下单或付款。"""
    return {"total_cents": quantity * unit_price_cents, "currency": "CNY"}


def main() -> None:
    if "--live" in sys.argv:
        from common import live_model

        model = live_model()
    else:
        # 固定模型计划，只验证协议与执行逻辑，不评价真实模型选工具能力。
        model = ScriptedChatModel(responses=[
            AIMessage(content="", tool_calls=[{
                "name": "calculate_total",
                "args": {"quantity": 3, "unit_price_cents": 1990},
                "id": "purchase-1",
                "type": "tool_call",
            }]),
            AIMessage(content="总价 5970 分，即 59.70 元；尚未下单。"),
        ])
    bound = model.bind_tools([calculate_total])
    messages = [HumanMessage(content="请调用工具计算 3 件单价 1990 分的总价。")]
    proposal = bound.invoke(messages)
    messages.append(proposal)
    if not proposal.tool_calls:
        raise RuntimeError("模型没有提出工具调用；检查模型能力、提示与工具描述")

    allowed_tools = {calculate_total.name: calculate_total}
    for call in proposal.tool_calls:
        if call["name"] not in allowed_tools:
            raise ValueError("模型提出了未授权的工具名")
        result = allowed_tools[call["name"]].invoke(call["args"])
        messages.append(ToolMessage(
            content=json.dumps(result, ensure_ascii=False),
            name=call["name"],
            tool_call_id=call["id"],
        ))
    answer = bound.invoke(messages)
    if answer.tool_calls:
        raise RuntimeError("本章只演示一轮工具调用；多轮循环见 Agent 章节")
    print("工具结果：", messages[-1].content)
    print("最终回复：", answer.content)
    assert calculate_total.invoke({"quantity": 3, "unit_price_cents": 1990})[
        "total_cents"
    ] == 5970
    try:
        calculate_total.invoke({"quantity": -1, "unit_price_cents": 1990})
    except ValidationError:
        print("负数数量：已正确拒绝")
    else:
        raise AssertionError("工具必须在执行前校验输入")


if __name__ == "__main__":
    main()

工具结果应包含 total_cents: 5970，固定最终回答给出 59.70 元。负数数量应被拒绝。tool_call_id 把一条工具结果对应到原请求，不能随便生成新 ID，也不能丢掉发起请求的 AIMessage。

代码只演示一轮工具调用：如果模型继续请求工具，就明确报错并指向 Agent 章节。这样不会把“一次调用的示例”误当作完整循环执行器。在线运行可添加 --live，但模型可能不选工具或再请求一步，这正是需要用真实集成测试观察的行为。

04把能力边界放在执行层

代码中的 allowed_tools 是固定白名单，模型返回的名字只能在这个映射中选择，不能据此动态 import 任意模块。实际项目还应按当前登录用户、租户与请求范围筛选能力，并在函数内核验访问权限。

模型参数与可信运行时上下文不同。商品数量可能来自用户问题；用户身份、租户 ID、数据库连接和 API 凭据应由服务端注入。不要给模型一个可自由填写的“管理员身份”参数。后续的 ToolRuntime 章节会演示传递可信上下文。

只读工具可以安全地重试某些临时错误，但写入工具可能已完成操作，只是响应在网络中丢失。此时盲目重试可能重复创建工单或重复扣款。写入前应设计幂等键、批准边界与审计记录，且批准针对明确的参数，而不是一句模糊的“允许工具”。

05练习：测试工具的边界

  1. 入门：将数量改为 2、单价改为 2500 分。验收条件：工具返回 5000 分；同时更新固定最终回答，避免把不一致的模拟文本误认为推理结果。
  2. 进阶：分别测试数量 0、数量 1001、字符串数量以及多余参数。验收条件：这些输入在乘法执行前被拒绝，合法整数参数仍成功。
  3. 挑战：把离线模型工具名改成未知名称，验证白名单拒绝。再模拟同一 AIMessage 中两个不同 ID 的合法调用，检查每个结果都带对应 ID，并保留原始调用消息。
参考检查思路

第三题可以比较请求 ID 集合与 ToolMessage.tool_call_id 集合是否相等，并检查数量一致。生产系统还需要处理工具异常、取消和超时，不能只验证快乐路径。

06常见误区与最佳实践

  • 绑定不等于执行。看见 tool_calls 后，应用仍需执行并回传结果。没有 ToolMessage，模型不知道真实执行结果。
  • 工具描述不等于授权。“只允许本部门访问”必须落实为代码与数据库约束，不能仅靠提示。
  • 工具输出也可能不可信。网页、工单正文或检索片段可能含恶意指令。它们是资料，不应升级为 system 规则。
  • 错误反馈要有用而有限。向模型返回可恢复的业务错误，向受控日志记录详细异常；避免把堆栈、连接串或员工信息直接交回模型。
  • 控制返回规模。工具一次返回几万条记录既慢又难读。优先分页、筛选与明确字段，让下游只拿到完成任务所需数据。
